# 后台终端处理预算

## 范围和验收

本地终端复用既有有序 Channel 和字节额度。可见终端优先解析，隐藏终端在应用级共享额度内轮转。隐藏终端继续运行并处理终端查询，切回时提升优先级；关闭、重启和组件卸载取消旧连接的排队任务。SSH 保持现有处理路径。

保留原有比较目标：30 会话后台持续输出时，前台输入 p95 比同轮空闲增加不超过 16 ms，前端待解析量不超过 1 MiB。另核对后台命令完成耗时、突发吞吐、切回首帧和已接收输出追上解析的耗时。原始报告只保存基准生成的编号和计数，使用隔离的应用与 CLI 集成配置目录。

## 调度前的测量

在专用构建中为固定版本 xterm 的解析函数增加耗时探针，按解析发生时的可见状态分别累计调用次数和同步耗时。这不是从消息收到到回调完成的等待时间，也不包含异步解析挂起期间或系统 GPU 耗时。探针验证实际解析方法存在，保留调用参数、接收对象、返回值和异常，并在释放时还原。

同机 30 会话的一轮记录在 `output/terminal-benchmark/output-scheduling/before/30-sessions.json`。后台持续输出阶段，隐藏终端发生 2,026 次解析，共用时 176.5 ms；可见终端 142 次，共用时 5.5 ms。突发阶段隐藏终端解析 2,638 次，共用时 204.9 ms。该轮前台空闲输入 p95 为 21.3 ms，后台持续输出时为 89.1 ms。不能把解析函数耗时直接解释成这两项延迟的全部来源；它是下一步调度试验的基线。

## 实现和回滚

调度器只经 xterm 的公开写入和完成回调接入正式应用；解析函数探针仅在专用基准构建中启用。可见和隐藏状态来自工作区已有的可见性，当前工作区的所有分屏都按可见终端处理。每个连接保持顺序，消费完成才确认输出。隐藏任务通过 MessageChannel 让出事件循环，不依赖只在窗口可见时触发的动画帧。断开连接释放待执行任务，旧连接完成回调不能推进新的连接。

测量探针、调度接入、实测报告分别提交。撤回调度接入提交可恢复原来的写入方式；无需迁移配置或会话数据。

首个试验每次只放行一个隐藏批次。30 会话负载下，前台 p95 为 39.9 ms，空闲为 21.2 ms，但突发输出耗时从基线的 826 ms 增至 4,548 ms。没有采用这一参数。报告保留在 `output/terminal-benchmark/output-scheduling/after-1/`。

调整后的候选每轮选择一个隐藏终端，最多放行八个已到达批次，全部完成后再选择下一个终端。本地传输的单批上限为 4 KiB，因此每轮最多 32 KiB。这样限制的是同时交给解析器的工作量，不承诺每轮解析一定少于固定毫秒数。原有单连接 128 KiB、全局 1 MiB 的输出额度继续覆盖队列和未确认输出。切回终端时保留已在处理的批次，随后按可见终端优先处理，不重复回放。

若一个终端的完成回调超过 8 ms 仍未返回，允许其他隐藏终端继续取得处理机会。等待中的终端仍保留当前批次，只有实际完成才确认输出，随后才执行它自己的下一组。这避免图片等异步解析把所有隐藏终端一起卡住。关闭、异常和旧连接回调的回归测试同时检查共享额度能够释放、旧任务不能恢复执行。

## 最终版本的验收

最终 Windows 构建的 SHA-256 前缀为 `afff25d24af2`，报告在 `output/terminal-benchmark/output-scheduling/final-1/`、`final-2/` 和 `final-3/`。首轮覆盖 1、10、30 会话，后两轮重复 30 会话。下面的 p95 均按各轮自己的样本计算，不能跨行相加。

| 30 会话指标 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
| --- | ---: | ---: | ---: |
| 空闲输入到 xterm 解析 p95 | 19.7 ms | 21.5 ms | 22.2 ms |
| 后台持续输出时，输入到解析 p95 | 52.2 ms | 39.0 ms | 51.7 ms |
| 同轮延迟增幅 | 32.5 ms | 17.5 ms | 29.5 ms |
| 持续输出时，前端收到到解析 p95 | 1.0 ms | 0.5 ms | 3.0 ms |
| 持续输出时，命令注入到 ConPTY 读出 p95 | 42.0 ms | 31.2 ms | 49.9 ms |
| 29 个后台命令完成 p95 | 4,236 ms | 4,127 ms | 4,153 ms |
| 所有会话突发完成耗时 | 1,166 ms | 1,059 ms | 1,027 ms |
| 突发解析吞吐 | 3.58 MiB/s | 3.93 MiB/s | 4.06 MiB/s |
| 突发待解析峰值 | 1,023.6 KiB | 1,023.7 KiB | 1,023.2 KiB |
| 持续输出时切回首帧 p95 | 49.9 ms | 39.4 ms | 49.1 ms |
| 切回后，已接收输出追上解析 p95 | 46.3 ms | 28.4 ms | 32.9 ms |

各档均通过收发字节和消息数平衡、探针完整配对、最终积压归零，以及每连接 128 KiB／全局 1 MiB 待解析上限检查。30 会话三轮共验证 60 次持续输出中的切换；每轮 29 个后台命令都完成，没有通过停止后台输出来取得前台响应。1 会话输入 p95 为 22.7 ms；10 会话空闲／持续输出的输入 p95 为 23.2／22.8 ms。

前端收到到解析这一段已缩短，但三轮端到端增幅仍全部超过 16 ms，性能目标尚未通过验收。残余较长等待出现在命令注入到 ConPTY 读出之间，该段包含输入 IPC、写入队列、Shell 和 ConPTY，现有探针不能把责任归给其中一个模块。下一项应拆分输入送达 Rust、写入 ConPTY 和读出响应的时间，避免继续收紧前端预算。

后续拆分和受控对照见 [本地终端输入延迟](terminal-input-latency.md)：应用输入路由与写入未呈现对应的排队，但稀疏响应暴露出批次等待过冲，已针对 Windows 等待机制修正。端到端结果仍须继续报告正常 Shell 的波动，不能以直接回显代替命令执行。

为避免只与一轮较慢的结果比较，又使用原构建 `93113ac9b421` 补跑两轮，保存在 `before-2/`、`before-3/`。改前三轮持续输出的前台输入 p95 为 89.1、42.9、85.5 ms，收到到解析的 p95 为 23.2、11.5、23.7 ms。调度后的前端排队段在三轮中都更短，但端到端仍有波动，不应宣称每次输入都比原版本快。

吞吐存在取舍：改前三轮突发完成耗时为 736–890 ms，解析吞吐为 4.68–5.66 MiB/s；调度后为 1,027–1,166 ms 和 3.58–4.06 MiB/s。后台持续输出的阶段完成时间则从 4,150–4,164 ms 变为 4,141–4,247 ms。共享预算改善了前台解析排队，降低了纯突发吞吐，并没有让后台命令停止。后续验收应同时保留这些指标。

## 回归检查

819 项前端测试、类型检查、注释策略检查、前端生产构建和普通工作台视觉回归通过。调度器测试包含轮转、公平推进、切回、关闭、异常、异步解析等待，以及真实 xterm 的分块 OSC、中文和查询回包。

设定 `PATTY_VISUAL_DISABLE_WEBGL=1` 后运行 `npm run test:visual:workbench`，浏览器测试确认 WebGL2 不可用且两个可见终端实际创建 Canvas 文字渲染层，再执行主题、分屏、命令和键盘焦点回归。此次检查通过，报告与截图在 `output/workbench-visual-canvas/`。这是 Windows 浏览器中的真实 Canvas 渲染和组件验证；原生 WebView2 的性能数字仍以桌面基准为准。
