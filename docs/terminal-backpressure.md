# 本地终端输出背压

## 测量口径

用 [Windows 多会话基准](terminal-baseline.md) 的同一套负载，采集 Rust 从 ConPTY 读到的字节、调用 Tauri 事件发送的字节和次数、前端交给输出处理路径的字节，以及 xterm 完成写入后扣减的待处理字节。专用构建只记录计数和基准生成的数字探针编号，不保留输出文本。原基线文件保留；分段报告写入 `output/terminal-benchmark/transport/`。

Rust 和前端按 20 ms 时间桶汇总。累计发送减接收是桶结束时跨进程待处理数据的近似值，可能漏掉桶内峰值。跨桶边界的阶段总数可能重叠，整轮收发总数另行核对。探针单独对齐输入、Rust 开始发事件和前端接收的时间，未完整匹配的探针不进入分段百分位。Rust 发送耗时是多个读取线程各自调用发送的耗时之和，不是 CPU 时间。

## 2026-11-04 分段实测

三组均使用同一台 Windows 11 机器、同一诊断构建（SHA-256 前缀 `29df589fa172`），各跑一轮。各组的整轮发送字节数、事件数都与前端接收一致，静置结束后 xterm 待处理量归零。下面两种队列的峰值可以出现在不同时间，不应相加。

| 指标 | 1 会话 | 10 会话 | 30 会话 |
| --- | ---: | ---: | ---: |
| 无后台输出时，命令到 xterm 缓冲 p95 | 21.1 ms | 21.8 ms | 26.9 ms |
| 后台持续输出时，命令到 xterm 缓冲 p95 | — | 23.1 ms | 84.2 ms |
| 后台持续输出时，Rust 发出探针到前端收到 p95 | — | 4.8 ms | 31.4 ms |
| 突发输出时，Rust 发出探针到前端收到 p95 | 3.7 ms | 86.7 ms | 400.4 ms |
| 突发输出时，已发送但前端未收到的近似峰值 | 12 KiB | 1.24 MiB | 3.16 MiB |
| 突发输出时，前端待 xterm 写入完成峰值 | 13.5 KiB | 0.75 MiB | 1.44 MiB |
| 突发阶段的 Rust 发送次数（按阶段时间桶） | 522 | 986 | 9,856 |

30 会话下，常规输入从注入命令到 Rust 发出探针的 p95 是 21.8 ms，后台持续输出时增至 37.7 ms。同一负载下，Rust 发出后到前端收到的 p95 也从 5.1 ms 升至 31.4 ms。不同阶段的 p95 不能直接相加。诊断构建增加了计数和时间采样开销；这组数据用于定位排队位置，不用它和未开启分段测量的数字计算性能回退。

大量事件既在跨进程链路积压，也在前端排队。只合并前端 `write` 会留下第一段积压，只合并 Rust 事件则仍允许发送端跑在消费者前面。下一步应同时验证短批次和从 Rust 到 xterm 完成写入的额度控制。

## 实施方案（4+1，已确认）

1. **目标。** 本地 ConPTY 使用每个连接一条 Tauri Channel。终端输出按短时间或大小合并，xterm 完成写入后回传已消费序号，Rust 据此放行后续批次。分别限制每会话与全局待处理字节，额度按会话公平分配；输出繁忙时，其他分屏的输入、缩放和查询回包仍能推进。回放、实时输出和退出共享同一顺序。以 30 会话前台 p95 增幅不超过 16 ms、前端积压不超过 1 MiB 为首轮比较目标。
2. **非目标。** 不改 SSH、Agent、通知、Shell 集成或滚动历史设置；不替换 ConPTY 或 xterm。未连接渲染器时保留现有有限回放语义，活跃流不丢字节。隐藏但仍挂载的会话继续消费输出。
3. **影响模块。** Rust 的 `pty.rs`、新输出队列与 IPC 入口，前端 `api.ts`、`TerminalPane`、本地输出消费及既有基准。后端在同一连接状态下交接回放和实时流。连接代际隔离 ACK，关闭和断线释放等待的额度；自然退出的尾部写入必须完成后才触发重启。Tauri Channel 负责有序投递，应用层额度负责背压。
4. **回滚。** Rust 与前端的本地传输迁移放在同一提交，一起撤回即可恢复现有事件路径。计数、协议夹具和实测报告可以保留。无配置或持久化迁移。
5. **提交顺序。** 先测试并实现有界队列与额度规则，验证慢消费者、多个会话、过期回执和关闭解阻；再同时迁移 Rust 与前端的本地流，验证回放交接、分块 UTF-8／OSC、末尾输出先于退出；最后跑真实 ConPTY 和三组基准，报告新旧差异及吞吐代价。

可选路线是在现有 Tauri 全局事件上加批次、连接代际、序号和回执，改动较小，但需要自行协调回放、数据、退出与监听器释放。推荐每连接 Channel，把这些消息绑在同一条流里。批次大小仍需在真实 WebView2 上试验，Tauri 对较大消息会走不同的传输路径。

批次期限由独立于阻塞读取的调度器处理，避免一小段输出等到下一次读取才显示。按连接代际累计确认已解析的序号，重复或旧回执不能释放新连接的额度。显式分离渲染器时切回有限回放；关闭则取消等待并回收额度。输入和终端查询回包继续走独立写入路径。

## 实施与首轮对比

本地连接已切换到有序 Channel。调度器以 4 KiB 或 2 ms 为发送条件，按会话轮转。Rust 待发送字节和已发送但未被 xterm 确认的字节共用额度：每连接 128 KiB，全局 1 MiB。这个上限计算 UTF-8 有效载荷，不含每个读取线程正在处理的一块数据、ConPTY 管道、序列化开销、滚动历史或图片缓存。未连接时，每会话保留至多 256 KiB 回放。显式关闭释放额度；自然退出等输出读完且收到最后一个确认，再交付退出消息。

以下是同机、同负载的首次对比，改动后构建的 SHA-256 前缀为 `576a22bac1e6`。原始报告保存于 `output/terminal-benchmark/transport-before/` 和 `output/terminal-benchmark/transport/`。运行 `npm run build:benchmark` 和 `npm run benchmark:terminals` 可重跑；设定 `PATTY_BENCHMARK_OUTPUT` 可把报告写入另一个目录，保留已有结果。

| 指标（改前 → 改后） | 1 会话 | 10 会话 | 30 会话 |
| --- | ---: | ---: | ---: |
| 无后台输出时，命令到 xterm 缓冲 p95 | 21.1 → 21.0 ms | 21.8 → 21.0 ms | 26.9 → 19.5 ms |
| 后台持续输出时，命令到 xterm 缓冲 p95 | — | 23.1 → 28.4 ms | 84.2 → 50.8 ms |
| 突发时，最后一批命令到 xterm 缓冲 p95 | 64.8 → 46.6 ms | 211.5 → 232.5 ms | 870.4 → 677.1 ms |
| 突发时，已发未收的近似峰值 | 12 → 4 KiB | 1,274 → 924 KiB | 3,240 → 848 KiB |
| 突发时，xterm 待解析峰值 | 13.5 → 12 KiB | 773 → 834 KiB | 1,471 → 576 KiB |
| 突发时，前端解析吞吐 | 2.07 → 2.78 MiB/s | 6.55 → 5.95 MiB/s | 4.59 → 5.81 MiB/s |
| 整轮发送消息数 | 2,100 → 163 | 6,621 → 1,331 | 22,235 → 4,965 |

各档的整轮 Rust 发送与前端接收字节数、消息数一致；静置结束时 xterm 无积压。30 会话前端积压低于 1 MiB，持续输出的输入延迟比改动前低 33.4 ms，但同一轮从空闲到持续输出仍增加 31.3 ms，尚未达到 16 ms 目标。10 会话突发的延迟和吞吐有所退步；这些单轮数字先作对比，不用作回归门槛。

同一构建额外复跑两轮 30 会话，原始报告分别保存在 `transport-repeat-2/` 和 `transport-repeat-3/`。三轮后台负载下的 p95 为 50.8、57.1、53.4 ms，相对各轮空闲增加 31.3、38.0、32.4 ms。突发时 xterm 待解析峰值为 576、769、645 KiB，三轮均低于 1 MiB。跨进程积压近似峰值为 848、969、939 KiB；各轮发送与接收总量一致，最后的前端积压都归零。改前的分段基准只有一轮，尚不能把改前后的差值当作稳定的回归阈值。

也用 6 KiB／4 ms 试跑两轮 30 会话（构建 SHA-256 前缀 `d95609ea6ac7`，报告在 `transport-6k/` 和 `transport-6k-repeat/`）。持续输出阶段发送次数从 2,041–2,272 降到 1,274–1,313，但前台 p95 升到 66.9–89.7 ms，突发完成也更慢。因此保留 4 KiB／2 ms。下一轮延迟分析应把命令到 ConPTY 读出、读出到 IPC 发送、前端收到到 xterm 解析分别测量；目前命令到发送这一段包含前两者，不能据此判断延迟来自 Shell 还是调度。

## 输入延迟拆分

保持 4 KiB／2 ms 和之前的工作负载。专用构建在每条命令注入时记起点，以合成探针编号配对四个时间点：ConPTY 读取到完整探针、Rust 开始发送最后一段、WebView 收到最后一段、xterm 缓冲出现完整探针行。探针跨块时按终端分别匹配，报告只保存编号、时间和字节计数。

首段包含输入 IPC、Shell 执行及 ConPTY 写出和读取，不能单独用来衡量 Shell。四段百分位使用同一组完整样本。报告列出未匹配及时间倒退超过 1 ms 的样本；Rust 与 WebView 的时钟之间保留毫秒量级的测量误差。比较慢样本时以同一条命令的四段耗时为准，不把四个阶段各自的 p95 相加。

2026-11-04 使用同一 Windows 专用构建（SHA-256 前缀 `e7c9b19c6e22`）跑了 1 会话校验和三轮 30 会话。原始报告在 `output/terminal-benchmark/latency-breakdown/` 的 `sanity/`、`round-1/`、`round-2/` 和 `round-3/`。各轮 30 会话的空闲输入、后台持续输出输入均完整匹配 20 条探针，突发阶段完整匹配 30 条。没有未匹配或时序异常样本。各轮收发总字节和消息数一致，最终 xterm 积压归零。

| 30 会话各阶段 p95（ms） | 空闲第 1 轮 | 负载第 1 轮 | 空闲第 2 轮 | 负载第 2 轮 | 空闲第 3 轮 | 负载第 3 轮 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 注入命令到 ConPTY 读出 | 17.2 | 23.8 | 19.5 | 34.1 | 26.1 | 18.9 |
| ConPTY 读出到 Rust 开始发送 | 3.4 | 3.1 | 3.2 | 2.6 | 2.8 | 2.6 |
| Rust 开始发送到 WebView 收到 | 0.6 | 24.8 | 0.8 | 38.5 | 0.8 | 19.8 |
| WebView 收到到 xterm 解析 | 0.3 | 29.1 | 0.2 | 21.8 | 0.2 | 23.9 |
| 注入命令到 xterm 解析 | 21.2 | 74.0 | 20.1 | 70.9 | 28.3 | 54.0 |

负载下的端到端 p95 比各轮空闲高 52.8、50.8 和 25.7 ms，均未达到 16 ms 目标。按每轮最慢的两条命令逐条配对，发送之后的两段共占总耗时的 56%–77%。例如第一轮的 p95 样本总共用时 74.0 ms，其中 25.2 ms 用在开始发送到收到，31.9 ms 用在收到到解析。持续输出期间，Rust 读出到发送的 p95 没有升高；更换批次大小不应是下一步优先项。这组新增探针的构建与前文的对比构建不同，只用同一轮空闲和负载对比来定位耗时。

30 个会话同时突发是另一种负载：xterm 待解析峰值为 544–802 KiB，仍低于 1 MiB；命令本身会先写出 2,048 行，再打印探针，不能把该阶段的探针耗时解释成键入短命令的延迟。下一轮优先通过 P3-04 测量隐藏会话的 WebView 主线程工作量，再试验限制隐藏会话单次交给 xterm 的工作量，让可见终端先解析。验证时保留后台输出的字节和顺序，并检查持续输出期间后台进程仍能推进、切回会话能及时显示。
