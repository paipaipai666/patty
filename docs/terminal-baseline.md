# Windows 多会话性能基线

## 复测方法

在 Windows 仓库根目录运行：

```powershell
npm run build:benchmark
npm run benchmark:terminals
```

可以用 `npm run benchmark:terminals -- 30` 单独复测 30 会话。每组启动新的原生 Patty 窗口；终端使用 Windows PowerShell、ConPTY 和产品使用的 xterm。专用构建不使用 WebView2 调试端口，以独立应用标识运行，拒绝在没有隔离测试请求时启动。测试不改 `USERPROFILE`，禁用 PowerShell 用户 profile 和 CLI 通知集成。关闭只清理此次启动的进程树和数据目录。

每组依次创建并激活全部会话，等真实 OSC 7 提示符和探测命令返回。随后测空闲、单个前台终端输入、后台会话持续输出、同时突发输出、切换工作区，以及输出停止后的空闲状态。持续输出每个后台会话发 25 批、每批 64 行，批间隔 150 ms；突发输出每个会话一次发送 2,048 行。每次输入和切换阶段采样 20 次。

结果写入 `output/terminal-benchmark/{1,10,30}-sessions.json`，包含可执行文件哈希、Windows 与 WebView2 版本、xterm 版本、视口尺寸、原始采样和汇总。同名文件由后续复测更新，比较两个版本前先保留各自的报告。

| 指标 | 量的是什么 |
| --- | --- |
| 启动 | 启动进程到首个 OSC 7；新建终端到该终端首个 OSC 7 |
| 输入延迟 | 注入 xterm 输入到探测行到达前端，以及到该行写入终端缓冲。包含 shell 执行和传输，不等同于键盘到物理屏幕的延迟 |
| 切回首帧 | 选择目标会话到其可见 xterm 发出首次渲染事件 |
| 输出与积压 | 已到达前端输出处理路径的 UTF-8 字节数；以 xterm 写入完成回调扣减。看不到仍在 PTY 或 IPC 内的队列 |
| 资源 | Patty 和其 WebView2 进程的工作集、专用内存、单核 CPU 百分比、最忙 GPU 引擎利用率和专用显存。工作集可能重复计入共享页；CPU 至少需要两次采样 |

短阶段若未命中进程采样，报告会保留空值。不要把空值当作零占用，也不要把短时突发输出的平均速率当作最大稳定吞吐。

## 协议回归

`npm test -- vtCompatibility` 使用真实 xterm 检查逐字节 UTF-8、宽字符占位、跨块 OSC 7、备用屏恢复、DSR 回包、滚动历史重排和分块 iTerm2 图片锚点。`DECSET 2026` 目前只验证序列不破坏文本和光标；尚未验证同步输出是否按帧呈现。图片测试验证落点与载荷，实际图片绘制沿用现有浏览器验收。

本机基线验证本地 ConPTY 的提示符、输入、输出及工作区切换。SSH 仍以现有环回服务器测试为传输回归，未测远端性能，也未把每条 VT 夹具在 SSH 下的行为标记为通过。

## 2026-11-04 首轮实测

Windows 11 build 26100，i7-12650H，16 逻辑核，约 32 GiB RAM，WebView2 156，xterm 5.5.0，Patty 2.0.17，1280 × 800 CSS 像素，DPR 1.5。三组使用同一 release benchmark 构建，SHA-256 前缀 `6878b14659c8`。每个会话数量运行一轮；输入和切换 p95 各基于 20 次采样。

| 指标 | 1 会话 | 10 会话 | 30 会话 |
| --- | ---: | ---: | ---: |
| 进程启动到首个提示符 | 1,059 ms | 997 ms | 1,092 ms |
| 前台命令到 xterm 缓冲 p95 | 20.3 ms | 24.1 ms | 20.6 ms |
| 后台持续输出时的前台命令 p95 | — | 24.5 ms | 52.9 ms |
| 切回首帧 p95 | — | 21.2 ms | 30.1 ms |
| 突发输出的前端待解析峰值 | 31.3 KiB | 863.0 KiB | 1,815.6 KiB |
| 突发阶段已解析速率 | 2.33 MiB/s | 6.69 MiB/s | 6.15 MiB/s |
| 空闲工作集 p50 | 412 MiB | 439 MiB | 465 MiB |
| 空闲专用内存 → 输出和切换停止后，p50 | 317 → 285 MiB | 348 → 550 MiB | 393 → 1,189 MiB |
| 空闲专用显存 → 输出和切换停止后，p50 | 115 → 89 MiB | 119 → 152 MiB | 109 → 424 MiB |
| 空闲 CPU p50，占单核 | 1.2% | 1.0% | 0.7% |

30 会话持续输出时，命令到达前端的 p95 已是 52.6 ms，和写入缓冲的 52.9 ms 接近；不能把持续负载下的延迟都归因于 xterm。突发阶段收到 6,421 块输出，待解析峰值为 1.77 MiB。输出停止后队列归零，专用内存和显存仍高于空闲起点。这个结果说明有保留的资源，不能据此判定泄漏或归因给某个缓存；下一轮要分别测长时间空闲、逐一关闭后台会话和 Canvas 回退。

## 下一项和暂定预算

先做输出路径的背压。第一步在 Rust 读取、IPC 发送和前端消费三个边界补齐计数，确认尚未到达前端的数据在哪里等待。随后验证短批次与 xterm 消费回执的方案，保证输入、查询回包、退出和重连仍能推进。对本地 PTY 先验收；SSH 要在同一套有序、无丢失、可取消的测试通过后再迁移。

| 检查项 | 下一轮目标 |
| --- | --- |
| 30 会话持续输出下的输入 | 同轮 p95 比无后台负载高不超过 16 ms |
| 30 会话突发积压 | 前端待解析峰值不超过 1 MiB；另外设置每会话与跨进程在途字节硬上限，分别验证，不能用一个数字代替 |
| 前台操作和吞吐 | 无负载输入及切回 p95 不回退超过一帧；在同负载下复测吞吐，记录限流代价 |
| 正确性 | 输出有序、活跃流不丢字节；尾部数据先于退出；关闭、重连和查询回包能解除等待 |
| 后台资源 | 30 会话静置无输出时，Patty 与 WebView2 合计 CPU p50 先以不超过单核 5% 为候选；内存与 GPU 先复测回落和关闭后的释放，暂不定硬上限 |

这些是本机首轮比较目标。修改前后使用同一机器、构建模式和工作负载各复测三轮，保存原始报告后再决定是否把目标设成回归门槛。
