# 本地终端输入路径的延迟

## 测量边界

本轮检验的假设是：前端解析预算生效之后，剩余输入等待来自应用的输入路由、写入队列或写入操作。专用构建增加四个时间点：Rust 命令处理函数收到输入、入队前、写入线程开始写入、写入及 flush 成功返回。与既有 ConPTY 读取探针和前端时间配对。生产构建不启用这些记录，不保存命令文本。

入队时间点在复制字节并发送到队列之前，因此排队一段也包含复制和发送的时间。写入成功返回不代表 Shell 已消费输入。写完到读到探针之间还包含 ConPTY、Shell、读线程调度，以及应用注入的 Shell 集成逻辑；不能把整个时间直接记为某个第三方组件的开销。

Rust 和前端的时间采用同一组完整匹配的合成探针，时钟保留毫秒量级误差。各段 p95 对应的样本可能不同，不能相加。

2026-11-04 使用同一专用构建，SHA-256 前缀为 `3c11ba6399e2`。单会话校验和三轮 30 会话的原始报告在 `output/terminal-benchmark/native-input/` 的 `sanity/` 和 `round-1/` 至 `round-3/`。每轮空闲和持续输出阶段各有 20 条完整匹配的前台探针，无缺失或时序异常。各轮通过收发平衡、最终积压归零和字节预算检查。

| 输入注入到 Rust 收到 | 0.514 ms | 0.373 ms | 0.417 ms |

## 下一项受控诊断

代码检查发现，PowerShell 的 `prompt` 每次都会调用 `__PattyRepairImageCursor`，同步请求本地图片状态，即使这轮命令没有输出图片。它是应用拥有的逻辑，属于“写入返回到读到响应”这一段的候选原因，尚未证实。

在隔离基准会话中对同一前台 PowerShell 做“启用、临时停用、恢复”对照，三组均保留相同的后台持续输出。只临时替换该进程内的函数，保存并恢复原 ScriptBlock，不改用户配置或正式 Shell 集成。通过 `finally` 执行恢复；基准完成后关闭临时进程。若停用没有稳定改善，则排除这条假设；若改善明显，再针对图片处理条件设计修正和回归覆盖。

## Console.ReadLine 对照

下一项诊断仍使用同一个前台 PowerShell 进程、ConPTY、输入队列和前端输出路径。临时执行一个 `Console.ReadLine` 循环，读取同样的探针命令文本并直接回显对应编号，分别测量空闲和后台持续输出；它不逐条执行 Shell 命令。收到停止标记后退出循环，再用正常 Shell 重跑后台负载。这个对照用于区分交互式命令处理与共同的控制台链路，不能作为真实 Shell 性能达标的替代结果。

构建 `30071e9cd0f9` 的三轮报告在 `output/terminal-benchmark/console-input-control/`。直接回显时，写完到读到响应的 p95 仅为 1.82–5.28 ms，但空闲时读到响应后开始发送的 p95 为 15.13、15.34、15.35 ms。这一段由应用自己的批次调度器负责，配置的截止时间为 2 ms，实际存在明显的等待过冲。恢复正常 Shell 后，写完到读到响应的 p95 回到 20.95–56.68 ms；因此控制台链路本身并不必然消耗这些时间，仍应把正常命令处理与应用输出等待分别计量。

## Windows 批次截止时间修正

原实现依赖条件变量的限时等待。本机稀疏输出的实测表明，2 ms 截止时间会拖至约 15 ms；持续流里其他到达通知会提前唤醒，所以原来的持续输出测量容易掩盖这一问题。

修正使用一个应用级唤醒事件和一个一次性可等待计时器。新输出、回执、断线或关闭触发事件；批次截止时由计时器唤醒。信号先于等待到达也会保留，状态改变之后始终重新检查队列。空闲时只等待事件，不循环轮询；忙碌时保留 4 KiB／2 ms 的批次规则以及原有字节额度。

优先创建高精度计时器，创建不成功时退回普通计时器；若原生等待资源均不可用，保留条件变量路径并记录诊断。微软文档注明高精度标志适用于 Windows 10 1803 及以后版本，零周期表示一次性计时器。[计时器创建](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw)，[相对截止时间和周期](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setwaitabletimerex)。

四项新增回归覆盖先发信号、数据打断后续截止时间、没有后续输出也能按截止时间唤醒，以及普通计时器回退。专用报告记录实际采用的等待模式，避免仅凭创建参数推断高精度路径已经启用。

## 修正后的对照结果

同机专用构建 `08c5f522919a` 完成了 1 会话校验和三轮 30 会话，报告在 `output/terminal-benchmark/precise-deadline/`。三轮记录的实际等待模式均为 `high_resolution`。表内为各轮 p95，列中的三个数按轮次排列，不代表一次请求的可相加阶段。

| 直接回显对照 | 修正前，第 1／2／3 轮 | 修正后，第 1／2／3 轮 |
| --- | --- | --- |
| 空闲时，读到响应到开始发送 | 15.13／15.34／15.35 ms | 2.39／2.40／2.38 ms |
| 空闲时，输入到 xterm 解析 | 18.0／17.3／18.0 ms | 6.7／6.8／5.1 ms |
| 后台持续输出时，输入到解析 | 19.2／22.2／18.3 ms | 19.6／13.7／11.9 ms |

三轮最终报告全部通过收发字节与消息数平衡、探针配对、结束后积压归零，以及单连接 128 KiB／全局 1 MiB 的待解析量检查。正常突发负载耗时 954–1,176 ms，吞吐为 3.54–4.37 MiB/s。压力下的额度等待仍可能使读到到发出的耗时超过 2 ms；本次修正解决的是无额度阻塞、只等待短批次截止时间的过冲。

正常 Shell 的标准输入阶段 p95 为 22.4、21.8、20.8 ms，后台持续输出时为 34.6、50.6、73.2 ms，同轮增幅为 12.2、28.8、52.4 ms。只有首轮达到 16 ms 目标，不能宣称端到端已经稳定改善。直接回显对照证明控制台和应用链路可更快完成；正常 Shell 的命令处理、输出投递和系统调度仍有波动，现有证据不足以把这些时间全部归给某一个组件。

## 验证和提交

2026-11-05 已完成[行编辑器与资源采样的限定对照](input-latency-controls.md)：保留真实命令执行后，简化编辑器仍不能消除负载尾延迟；关闭 GPU 采样也未使正常 Shell 稳定达到 16 ms 增幅目标。六次恢复原编辑器后的增幅为 22.1–30.0 ms。输入排队和写入仍很短，现有证据不支持重写输入队列。

随后按批准上限完成一次单会话校验和两次 30 会话的 [Shell 内部分段计时](shell-latency-tracing-results.md)。40 条带计时的负载探针中，最长区间均在输入写完到编辑器返回之间；命令识别 p95 为 0.56／0.99 ms，输出调用开始到 ConPTY 读回为 0.65／0.64 ms。识别返回到实际命令开始之间另有 22.67／27.84 ms 的 p95，仍混合了应用剩余包装逻辑、PowerShell 派发和诊断函数入口，不能全部归为某一组件。

诊断命令增加了函数调用和文本长度，开关记录后的差值也不稳定，因此不能用它精确分解未修改的正常命令。正常命令四组增幅为 21.1、13.6、13.0、11.8 ms，结合此前失败记录，16 ms 目标仍未稳定达标。本轮不再追加参数测试，也没有据此修改正式编辑器、分类器或输出队列。
